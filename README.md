# Element Mark

给 GUI 中的材料物品绘制化学元素符号角标（Zn、Cu、Fe……），位置可选四个角落。

不绑定任何具体模组：符号通过物品的 **矿辞 tag（ore dictionary / common tag）** 解析，因此凡是遵循 `c:` / `forge:` 材料 tag 规范的模组（格雷科技、ChemLib、Create 等）都能自动生效。

## 工作原理

1. 客户端 mixin 注入 `ItemRenderer.render` 的 `TAIL`，仅在 GUI 展示语境下追加绘制。
2. `BadgeResolver` 读取物品 `Holder` 上的 tag，只认 `c:` / `forge:` 命名空间、路径形如 `<form>/<material>` 的 tag（如 `c:plates/zinc`），取 `/` 后段作为材料名。
3. 材料名先查**用户配置**，再查内置 118 元素表；命中则绘制缩写，两处都无命中则不绘制。
4. 结果按 `Item` 缓存在 `ConcurrentHashMap`，每个物品只解析一次；配置重载时清空缓存。

## 配置界面

模组列表（`模组` → 找到 Element Mark → `配置` 按钮）内置图形界面，可直接调整三项，改动即时生效并写回配置文件：

| 控件 | 作用 | 对应的配置项 |
| --- | --- | --- |
| 角落按钮 | 循环切换 `top_left` / `top_right` / `bottom_left` / `bottom_right` | `corner` |
| 滚动方式按钮 | 在「左右摆动」与「单向循环」之间切换，只影响放不下的超长缩写 | `scroll` |
| 尺寸滑动条 | 拖动调整缩写大小，区间 `0.9 ~ 1.1`（两个端点都有几何依据，见下） | `font_scale` |

另有「重新读取配置」按钮，手改配置文件后点一下即可看到效果（三个控件的显示都会跟着同步）。

界面上始终绘制样例物品预览（铁矿 / 铁块 / 铁锭，三者都解析为 `Fe`）。

> 预览不写任何自己的绘制代码：样例物品就是普通的 `GuiGraphics.renderItem`，角标由 `ItemRenderer.render` 那支 mixin 照常画上去，与物品栏、容器走的是同一条路径。所以"预览和实机不一致"在结构上不可能发生。
>
> 早期版本曾在预览里用 `drawString` 重画一遍角标，那正是预览与实机对不上的根源——两条渲染路径的字体粒度与缩放锚点都不一样，靠调参数对齐永远会有残差。

## 配置文件

位置：`config/elementmark.txt`，首次启动自动生成。

格式为每行 `<段名>:<值>`，`#` 起始行与空行忽略，段名不区分大小写。除保留段名外，其余段名一律视为**材料名**：

```
redstone:红石            材料名 redstone 的物品绘制「红石」
lapis:青金石             同上
zinc:Zn                  覆盖内置元素表的默认值
empty:                   值留空表示隐藏该材料的角标

corner:top_left          保留段：绘制角落 top_left / top_right / bottom_left / bottom_right
font_scale:0.9           保留段：缩写尺寸系数，在自动适配的基础上再乘一次，区间 0.9 ~ 1.1
scroll:loop              保留段：超长缩写的移动方式，sway（左右摆动）| loop（单向循环）
```

上面三段的出厂默认就是 `top_left` / `0.9` / `loop`（代码里的 `DEFAULT_CONTENT` 与之一致）：这一套是实测比对后选定的偏好，新装玩家上手即"调好的状态"，不必自己再摸一遍。

改完存盘后，按 `F3+T` 重载资源即可生效，无需重启游戏。配置界面里也有「重新读取配置」按钮，改完 `font_scale` 不用来回退出界面。

模组不注册任何按键绑定：重载只有 `F3+T` 与配置界面按钮两个入口。

### 尺寸说明

`font_scale` 与自动适配**相乘**：自动适配负责"不超出图标"，`font_scale` 负责在这个基础上再放大或缩小。`1` 是数学基线（只用自动适配的结果）；**出厂默认取滑条下限 `0.9`**，配置界面里的滑动条改的就是它。下限这端顺带还让滚动行一次多看见一点字（0.9 档可见 3.70 个字形位置，1.0 档 3.33），而超长缩写恰恰最需要这个。

区间 `0.9 ~ 1.1` 的两个端点都是算出来的，不是拍的：

| 端点 | 值 | 依据 |
| --- | --- | --- |
| 下限 | `0.9` | 实测：**0.9 倍下三个全角字的大小**就是文字还能看清的底线，即 `0.667 × 0.9 ≈ 0.6`。滑条不允许再往下调 |
| 上限 | `1.1` | 自动适配保证了未滚动文本的渲染宽度 ≤ `18`，乘 `1.1` 最多 `19.8`，仍小于图标边长 `20`。上限之内**角标绝不越出图标**，再放宽就会压到相邻槽位 |

于是"字最小能多小"由两个独立的量共同决定：自动适配下限 `0.667`（三个全角字刚好填满可用宽度，见下节）与滑条下限 `0.9`，两者相乘 `≈ 0.6` 就是屏幕上会出现的最小字号。

它**一起参与布局**：右对齐/下对齐的锚点按最终渲染宽度算，所以改字号时文字始终贴住所选角落，不会从角上溢出去。这也是为什么模组只提供"角落 + 尺寸"两项——定位本身已经是几何精确的，没有留给手动微调的余量。

历史上曾有过 `offset_x` / `offset_y` 两个微调项，实测调出的原始值与其去向：

| 参数 | 实测原始值 | 去向 |
| --- | --- | --- |
| `offset_x` | `-10` | 已被 `ANCHOR_X` / `ANCHOR_Y` 吸收（它就是 `-ICON_SIZE/2`） |
| `offset_y` | 上角落 `-7`、下角落 `-5` | 已被"纵向从字形框顶边量起"的公式吸收（见下文） |

两个数字都是**验证依据**（它们精确等于 `ASCENT` 与 `ASCENT - DESCENT`），公式修正后便不再需要，故配置项已移除。

**缩放锚点必须在笔位上。** 绘制矩阵是 `T(笔位) × S(字号)`——先平移到笔位再缩放，于是缩放围绕笔位进行，贴边的那一侧在任意字号下都固定不动。早期写法是"先平移到图标原点、再缩放、然后在缩放域里给坐标"，等于把坐标又乘了一次字号，改字号时文字会非线性漂移（表现为"字号一变，位置就跑，像围绕图标原点缩放"）。

**为什么有时左右切换看不出差别。** 左对齐左缘恒为 `PAD`、右对齐右缘恒为 `ICON_SIZE - PAD`，两者的差值 = `可用宽度 - 文本渲染宽度`，也就是"余量"。文本把可用宽度撑满时余量为 0，左右自然重合——这是几何必然。文字越短、`font_scale` 越小，余量越大，左右差异越明显（例如 `C` 在 `font_scale:1` 下左右相差约 13 字形单位）。

## 自动缩放

缩写宽度超过图标可用宽度时按比例缩小，保证不超出物品图标范围：

| 参数 | 值 |
| --- | --- |
| 图标边长 | 20 字形单位（16 屏幕像素） |
| 左右内边距 | 各 1 字形单位 |
| 可用宽度 | 18 字形单位 |
| 缩放下限 | 0.667（= 三个全角字 27 刚好填满可用宽度 18 的适配值） |

只需约束宽度即可：原版字体行高 9 字形单位远小于可用高度 18，且缩放为等比，高度约束恒成立。

下限停在 `0.667` 不再往下的原因见下节——字数更多时不再缩，而是改为滚动。

## 超长文字：框内独占一行（溢出小则静止，大则滚动）

**触发条件**：即使把自动适配压到下限 `0.667` 也贴不进角落，等价于宽度 > `18 / 0.667 = 27` 字形单位，对 CJK 就是**第 4 个字起**。此时字号就地停在下限、不再缩小，位置从"角落对齐"改为**在图标框内独占一行**：

| 角落的纵向分量 | 滚动行落在哪 |
| --- | --- |
| 上排（`top_left` / `top_right`） | 图标框内**上半**那一行：字形框顶边贴框内上缘 `PAD` 处 |
| 下排（`bottom_left` / `bottom_right`） | 图标框内**下半**那一行：字形框底边贴框内下缘 `ICON_SIZE - PAD` 处 |

横向窗口取框内可用宽度（`SCROLL_WINDOW = ICON_SIZE - PAD × 2 = 18`），与贴角落时的可用宽度是同一个值——所以"刚好贴进角落的三个全角字"与滚动行占的是同一段横向区间，由静态切成滚动时横向不会跳一下。窗口本身不能再宽，否则会压到相邻槽位上的物品；实际**可见**范围则每侧额外放宽 `PAD`（于是裁剪范围正好是整块图标），见下面「可见范围」一节。

### 两种移动方式（配置项 `scroll`）

| 值 | 动作 | 特点 |
| --- | --- | --- |
| `loop`（默认） | **单向循环滚动**：自窗口右缘外侧滚入 → 向左滚出窗口 → 紧接重来（无缝循环） | 移动方向恒定，更像跑马灯；每个字都不停，节奏连贯 |
| `sway` | **左右往返摆动**：开头对齐窗口左缘 → 向左摆到末尾对齐窗口右缘 → 再摆回来，两端各停 `0.6` 秒 | 两端一停，开头与结尾各有 0.6 秒可读时间；代价是节奏有停顿 |

两种方式共用速度 `24` 字形单位/秒（≈19 屏幕像素/秒），都在同一个窗口里移动、都做逐字裁剪。方式只影响"长到必须动起来"的角标——放得下的贴角落、放不太下的静态居中（见下），与本节无关。

### 可见范围：每侧放宽 `PAD`，裁剪范围正好 = 整块图标

绘制窗口 `SCROLL_WINDOW = 18` 只有三个字宽，而滚动行的字号被钉在缩放下限，所以**裁剪范围**每侧额外放宽 `CLIP_SLACK = PAD`（`1` 字形单位）：`PAD + SCROLL_WINDOW + PAD = ICON_SIZE`，裁剪范围恰好等于整块图标 `[0, 20]`。

| `font_scale` | 每字宽 | 可见字形位置 | 其中完整 | 裁剪范围越界 | 半格越界 | 越过 2 px 空隙 |
| --- | --- | --- | --- | --- | --- | --- |
| `0.9` | 5.4 | 3.70 | 2.70 | 0 | 2.2 px | 0.2 px（亚像素）✅ |
| `1.0` | 6.0 | 3.33 | 2.33 | 0 | 2.4 px | 0.4 px（亚像素）✅ |
| `1.1` | 6.6 | 3.03 | 2.03 | 0 | 2.6 px | 0.6 px（亚像素）✅ |

不放宽时只有 `18 / 5.4 = 3.33` 个字形位置（0.9 档）——这正是用户反馈的"滚动起来基本只能看见三个字"。放宽到 `PAD` 后是 `20 / 5.4 = 3.70`，**提升有限，因为上限已被物理量钉死**：图标恒占 16 屏幕像素、槽位间距 18 像素，相邻槽位间只有约 2 像素空隙，可见范围最远只能到整块图标（`20` 字形单位），再多就是别人家的物品了。（想同时看见更多字只能把滚动行的字号再调小，即把可读性基准 `READABLE_GLYPHS = 3` 往上调——但那正是用户拍板的下限，再小就认不出了。）

判据是"字形**中心**落在裁剪范围内"，所以字形还会再探出半格——上表"半格越界"列。裁剪右缘压在图标右缘上时，那半格越过约 `2` 像素空隙后只剩 `0.2 ~ 0.6` 像素，**亚像素级**（且只发生在某个字中心恰好压线的瞬间），实机看不出。**这一栏曾经失控**：首版把 `CLIP_SLACK` 取到半个字宽（`4.5`），裁剪右缘本身就落在图标右缘外 `2.8` 像素、已经在相邻物品的地盘里，叠加半格后最坏越界近 `5` 像素——用户实测反馈"有些压到旁边格子了"，故收到 `PAD`。

放宽只作用在裁剪上：文字移动的起止仍按 `SCROLL_WINDOW` 算，所以"摆动两端对齐窗口边缘"的语义不变，只是边缘那几个字能多露出一点。

> 单向循环的"看不到字"的时长约 `0.22` 秒，且几乎全部来自裁剪判据本身：末端字要在字形**中心**越过左缘时才算消失、开头字要等中心进入右缘才出现，两端各多出半个字宽，合计正好一个字宽。空档常量 `SCROLL_GAP` 已取 `0`——首版取 `8`（约一个字宽）时实测"两次滚动之间间隔太长"，因为真正的空白是 `(空档 + 一个字宽) / 速度`，加起来约 `0.56` 秒，肉眼就是"卡了一下"。

### 溢出不足一个字宽：静止居中

溢出量（渲染宽 − 窗口）小于**一个全角字宽** `9` 字形单位时**不动**，直接静态居中：溢出不足一个字，文字左右各只压出半格以内，那半格落在 `PAD` 与槽位间隙里（约 2 屏幕像素），内容基本完整可读——此时滚动的收益（让某个字完整露出来）抵不过代价（整行一直在动、反而总有一个字在外）。**四个字这一档就落在区间内**：`font_scale` 0.9 ~ 1.1 全档位溢出只有 3.6 ~ 6.6 字形单位，静止居中即可完整看清四个字。

> **静态居中这条路径不做窗口裁剪**（这里栽过一次）。裁剪只用于"动起来"的两种情况——那时文字大部分在窗口外，不裁会压到相邻槽位；而静态居中的语义本就是"内容基本装得下、两侧各压出不到半格"，那半格有意留在窗外。
> 曾经两条路径共用裁剪，四个字就只剩中间两个：居中后首尾两字各有半个字探出窗口，按"字形**中心**落在窗口内"的判据，它们的中心恰好落在窗口外零点几单位而被整块吃掉。而 `font_scale = 1.0` 时首字中心正好 = 0、末字中心正好 = 窗口右缘，卡在判据等号上，所以这个 bug 在 1.0 从来没暴露，一调到 1.01 两个中心同时越界、两字同时消失（详见核算脚本第 6 节）。

各字数下的实际表现（`font_scale:1`，CJK 每字 9 字形单位，核算脚本 `.workbuddy/notes/scroll_check.py`）：

| 字数 | 文本宽 | 最终字号 | 渲染宽 | 溢出 | 表现 |
| --- | --- | --- | --- | --- | --- |
| 2 | 18 | 1 | 18 | 0 | 贴角落，恰好填满可用宽度 |
| 3 | 27 | 0.667 | 18 | 0 | 贴角落，填满（**缩放下限**） |
| 4 | 36 | 0.667 | 24（0.9 档 21.6） | 6 / 3.6 | **静态居中**（溢出 < 一个字宽），不裁剪 |
| 5 | 45 | 0.667 | 30（0.9 档 27） | 12 / 9 | **滚动**（`sway` 摆 / `loop` 循环），裁剪 |
| 10 | 90 | 0.667 | 60 | 42 | **滚动**，裁剪 |

> **坐标系换算只适用于两类量中的一类**：滚动绘制发生在 `pose.scale(textScale)` 之后，所以
> （a）窗口宽度、速度、最小摆幅、空档、描边粗细这些"按屏幕上多大定义"的量要 `× 1/textScale` 换回绘制单位；
> （b）`font.width(...)` **不用换**——MC 摆放字形本就是"1 度量单位 = 1 绘制单位"。
> 给 (b) 多乘一次就是字距被放大 `1/textScale` 倍（0.667 时每字之间凭空多出约半个字宽的空隙）；
> 漏乘 (a) 则是窗口只剩应有一半宽、文字从窗口内部起步。

> **为什么用逐字裁剪而不是 scissor**：绘制发生在 `ItemRenderer.render` 的 TAIL，手上只有已经变换过的 3D 矩阵，拿不到槽位的屏幕坐标；要用 `RenderSystem.enableScissor` 就得把矩阵反推回屏幕像素（GUI 缩放、投影矩阵都得自己再算一遍），而"某个量在哪个坐标系里代表什么"恰恰是这个模组踩过多次的坑。逐字裁剪只在本地度量里比大小，不引入任何新的坐标系假设。
>
> 裁剪判据取"字形**中心**落在窗口内"，而不是"字形完整落在窗口内"：后者会让一个有八成正落在窗口里的字被整块抹掉，文字移动时这个突跳反复出现很扎眼；前者把显隐挪到露出/遮住一半的时刻。这里的"窗口"是**裁剪范围**（绘制窗口每侧再放宽 `CLIP_SLACK = PAD`，即整块图标），所以字形最多越出图标右缘半格——0.9/1.0/1.1 三档各约 `2.2 / 2.4 / 2.6` 屏幕像素，而槽位间空隙有约 `2` 像素，只剩 `0.2 ~ 0.6` 像素的探入，肉眼不可见。

## 坐标定位

绘制只发生在 `ItemRenderer.render` 的 `TAIL` 一处。定位逻辑集中在 `BadgePlacement`（纯计算，输出"图标左上角为原点、单位字形单位、y 向下"的坐标），`ElementMarkClient` 负责把它映射进 3D 矩阵空间。

配置界面预览共用同一条路径（预览只调 `renderItem`，角标由同一支 mixin 画），因此不存在"两套坐标要对齐"这件事。

### 矩阵链（结论取自字节码，非推测）

`GuiGraphics.renderItem` 施加的是：

```
translate(x + 8, y + 8, 0)          // 原点 -> 槽位中心
mulPoseMatrix(scaling(1, -1, 1))    // 独立矩阵做 y 翻转
scale(16, 16, 16)                   // ★ 三分量全正
```

注意 y 翻转来自那个**独立的 `mulPoseMatrix`**，`scale` 本身是全正的 —— 早期把它当成 `scale(16, -16, 16)` 会推出相反的方向结论。

随后 `ItemRenderer.render` 先 `pushPose()`，经 `ForgeHooksClient.handleCameraTransforms`（对 `generated` 类贴图物品是恒等），再执行一次 `translate(-0.5, -0.5, -0.5)`。该 translate 与开头的 pushPose 配对（末尾 popPose），foil 分支另有自己的 push/pop。

### 原点落在图标哪个点：中心

**矩阵原点 = 图标中心。** 依据是实测反解而非纸面推导：某次实测发现要让文字贴住图标左缘，需要一个 `-10` 的水平位移，而 `-10` 恰好是 `-ICON_SIZE/2` —— 从原点到左边界正好半个图标宽。该位移现已写死在 `ElementMarkClient.ANCHOR_X` 里。

> 纸面推导在这里翻过两次车。外层 `translate` 给 `+8`、内部 `T(-0.5,-0.5,-0.5)` 经 `scale(16)` 放大后给 `-8`，两笔相加只剩 `+8`——那是"槽位左上角到图标中心"的距离，容易被误读成"到左边界"。这类量的物理含义必须以实测为准，不能靠累加常量。

我们在 `TAIL` 处再 `scale(0.05, -0.05, 0.05)` 把单位变成"字形单位"（1 字形单位 = 0.8 屏幕像素，图标即 20 字形单位见方），该负号把 y 再翻一次，于是**本坐标系里 y 向下**。

### 对齐到左上角

`ElementMarkClient.ANCHOR_X` / `ANCHOR_Y` 均取 `-ICON_SIZE / 2`：把原点从图标中心搬到左上角。此后坐标即与 `BadgePlacement` 的"图标左上角原点"参照点重合，无需任何额外偏移。

### 字号如何进布局

**纵向的 y 是字形框顶边，不是基线。** 这一点曾是本模组的错源，证据写在这里：`Font.drawInBatch` 的 y 经 `drawInternal → renderText → Font$StringRenderOutput.accept` 原样传递（只额外加阴影偏移），最终进入 `Font.renderChar`；而同一段字节码里，删除线画在 `y + 4.5`（= `lineHeight / 2`，正是字形竖直中部）、下划线画在 `y + 9`（= `lineHeight`，即基线再往下 `DESCENT`）。若把 y 当基线，这两个数字都解释不通。

于是字形占 `[y, y + 9t]`，基线落在 `y + 7t`。对齐规则：

| 对齐 | 锚点 | 公式 |
| --- | --- | --- |
| 靠上 | 字形框顶边落在 `top` | `y = top` |
| 靠下 | 可见底沿（= 基线）落在 `bottom` | `y = bottom - 7t` |

靠下不能写成 `bottom - 2t`：字形框在基线之下还留着 `DESCENT = 2` 的空槽，而拉丁字母与 CJK 的可见底沿就是基线本身（只有 g / j / p / q / y 这类下伸字母才用得到那个空槽）。写成 `bottom - 2t` 会让文字整体偏低 `5` 个字形单位——历史上用配置项手动微调时实测到的"上角落要 `-7`、下角落要 `-5`"，正是本公式的验证依据（`7` 与 `5` 分别等于 `ASCENT` 和 `ASCENT - DESCENT`）。

其中 `t` 是**最终字号** = 自动适配 × `font_scale`。这一点必须成对使用：

- **位置**的右/下对齐锚点依赖 `width × t`；
- **字号**直接就是 `t`。

若位置计算漏掉 `font_scale`（历史 bug），调字号时文字会围绕左上角"长大"，看起来像围绕一个错误的中心缩放，且左右角落切换在长文本下会算出同一个坐标（文字恰好撑满可用宽度时 `left` 与 `right - width×t` 相等，属几何必然）。

./gradlew build

产物在 `build/libs/`。

## 开发环境

基于 [ModTemplatez](https://github.com/ZZZank/ModTemplatez)（Architectury Loom）。

- 元数据集中在 `gradle.properties`（`mods.toml` / `pack.mcmeta` 由 `processResources` 填充变量）
- 依赖加在 `gradle/scripts/dependencies.gradle`
- 运行 `genIntellijRuns` 生成 IDEA 的 Client / Server 运行配置
- 路径中不要含中文以外的编码问题风险项，clone 后先跑一次 `runClient` 再跑 `genIntellijRuns`
